Post the proof,
not the hype.

What it is, in plain words: a checker for announcements. Before a release note, a launch post, a README or a changelog goes out, post-proof reads it next to the record of what was actually built (did the site answer, did CI pass, what did the tests score) and stops it if it claims anything that record does not show, naming the exact words to fix. No AI judges the writing: it is a short, fixed set of rules you can read.

AI writes announcements faster than anyone can check them, and one overclaim ("live" before anything answers, "all tests pass" when CI failed, a perfect score the tests never reached) discredits the true claims beside it. post-proof is the gate between the draft and the publish button: a post may claim only what a build-receipt backs. Anything it cannot back is refused, with the exact words named.

Start here

Seven steps. Everything runs in this page; nothing you type leaves your browser.

  1. Under Try it, press Load a hyped draft, then ▶ Gate the post. The gate lists every claim it could check and refuses each one the build-receipt beside it does not back, with the reason.
  2. Press Load an honest draft and gate it again. Every checkable claim is backed, so it passes.
  3. Press Seal the current draft: a passed post is sealed to the receipt behind it (two SHA-256 hashes). Then press Tamper with the seal and watch the seal break.
  4. Under the ledger, press Run the honest + hyped drafts onto the ledger, then flip a refused post to "shipped". The hash chain breaks at exactly that entry.
  5. Now use your own: paste a draft, and a receipt of your own build in the same JSON shape (the box shows it). Edit the receipt (say "live": false) and gate again to see which claims fall.
  6. To use it for real, give it to your AI agent or add one step to CI: see For your agent and CI.
  7. To see what it would take off your team, put your own figures into the cost case.

Why announcements lose the room

0
models in the loop
Each claim is checked against the receipt by a fixed rule. No AI grades another AI's marketing, so the same draft and the same receipt get the same answer every time.
7
kinds of claim it checks
Links, "live" (and "launched", "out now", "now available"), "CI green", "verified / clean", K/N scores, percentages and multipliers ("3x faster"): the claims a reader takes as fact. A plain number ("seven layers") or a date ("5/11/2026") is left alone.
3.7
the UK advertising rule
CAP Code rule 3.7, enforced by the Advertising Standards Authority: hold documentary evidence for an objective claim before you publish it. The US FTC asks the same (a reasonable basis, before dissemination). post-proof makes that check mechanical for the claims it checks.

Try it: gate a draft against its receipt

A draft post, and the build-receipt behind it: what real probes saw (a live 200, CI's conclusion, the mutation-test score, measured facts). The receipt loaded here is agent-proof's, a sibling tool. The gate names every claim it can check and refuses the ones the receipt does not back. This runs the gated kernel.mjs, injected verbatim.

The post-receipt: sealed to its backing proof

A post that passes the gate seals a content-addressed receipt: the post's hash, the build-receipt's hash, the backed claims. It verifies anywhere, and the gate refuses to seal a post that failed.

The post ledger: every claim made, and what backed it

Each gate decision, shipped or refused, lands on a SHA-256 hash chain: the record you show when anyone (a reviewer, an auditor, your own future self) asks what was claimed and what backed it. Tamper with any entry and the chain breaks at that entry.

How it works, traced from a real run

This is the run in examples/refuse.json: the same input CI runs the shipped script on at every push. The numbers in the diagram are read from its committed output by make-page.mjs, and CI fails if they drift.

Step by step

  1. The draft goes in. A plain text, or a hook, a reveal and a call to action, which postText() joins.
  2. The checkable claims come out. extractClaims() finds links, K/N scores ("41/43", "4.9/5") and percentages of any length (a percent written "30%", "30 percent" or "30 per cent"), multipliers ("3x", "10×"), and the words "live / shipped / deployed / in production / launched / released / rolled out / out now / now available / generally available", "CI green / CI passed / all checks passed / the build is passing / tests are green", "verified / witness-clean". Each claim is named as written. A link is one claim: nothing inside it is read as another. A date ("5/11/2026") is not a score. Anything else is prose, and prose is not judged.
  3. Each claim is matched to the field that can prove it. checkClaims() backs a link only if it is the live product URL (and a 200 was seen) or a whitelisted link; "live" only if a 200 was seen; "CI green" only if CI concluded success; "verified" only if the mutation test was clean; a score only at the exact killed/total, or a fact stating the same K/N; a percent only if a measured fact states the same number as a percent; a multiplier only if a measured fact states the same multiplier.
  4. One unbacked claim refuses the post. gatePost() answers SHIP only when every checkable claim is backed, and names each unbacked one with its reason, so the writer (or the agent) fixes exactly those words.
  5. A shipped post is sealed. makePostReceipt() binds the post's SHA-256 to the receipt's SHA-256 and the backed claims, and refuses to seal a post that failed.
  6. Every decision is logged. appendPostLedger() adds shipped and refused posts alike to a hash chain; verifyPostLedger() finds the first entry anyone changed.

A report quotes each claim as written, punctuation included. Before a link is compared, a full stop, comma, colon, semicolon, "!", "?", "…" or closing quote at its end is dropped: that is why https://example.org/csv-checker., at the end of a sentence, is backed by a receipt URL without the full stop. A link ends at <, >, a double quote or a backtick, which cannot stand in a link unencoded, so a link in Markdown (<https://…>, [text](https://…)) or an HTML href is read as the link itself.

For your agent and CI: the claim-receipt-gate skill

The same gate you just used on this page ships as one file an AI agent can run before it publishes anything: a release note, a README, a changelog, a launch post. The agent hands it the draft and the receipt of what was actually built; the gate answers SHIP or REFUSE and names every claim the receipt does not back. The agent's words never get past it on their own say-so.

Three ways in

  1. In this page. Paste a draft and a receipt in Try it, press gate. Nothing leaves your browser.
  2. On the command line (Node.js 20 or later). Clone the repo, then node scripts/claim-receipt-gate.mjs examples/refuse.json. Exit 0 = SHIP, 1 = REFUSE, 2 = the input could not be used, 3 = an internal error (the script itself failed; the message is on stderr). The input is one JSON object: {"post": …, "receipt": {"url","live","ci","witness","facts"}, "sealedAt"?}.
  3. As an agent skill. Give your agent SKILL.md and the script. Its rule: before posting, run the gate; on REFUSE, fix or cut each named claim and run it again; never publish on REFUSE, and never edit the receipt to make a post pass.

In CI: one step

- name: the release note may claim only what this build proved
  run: node scripts/claim-receipt-gate.mjs release-note.json

A non-zero exit fails the job, so a refused note never reaches the publish step. Build release-note.json from the probes your pipeline already runs: the HTTP check on the live URL (live), the CI result (ci), the test or mutation score (witness), and any measured figure you want to quote (facts).

In CI: building the receipt from the run's own probes

A worked example for GitHub Actions, placed after your build and test steps. A step only runs when every step before it passed, so ci is "success" by construction; the live check is a real HTTP request made by the runner (not by the gate). Copy scripts/claim-receipt-gate.mjs into your repository first.

- name: build the receipt from this run's own probes
  env: { URL: https://your-product.example/ }
  run: |
    code=$(curl -s -o /dev/null -w '%{http_code}' "$URL")
    node -e '
      const fs = require("fs");
      fs.writeFileSync("release-note.json", JSON.stringify({
        post: fs.readFileSync("RELEASE_NOTE.md", "utf8"),
        receipt: { url: process.env.URL, live: process.argv[1] === "200",
                   ci: "success", witness: null, facts: [] }
      }));' "$code"
- name: the release note may claim only what this build proved
  run: node scripts/claim-receipt-gate.mjs release-note.json

Add your test or mutation score as witness and any measured figure you want to quote as a fact; leave them out and any score, percent or "verified" in the note is refused. For a ledger of every decision, your publishing script imports kernel.mjs and calls appendPostLedger: the one-file script gates and seals, it does not keep a ledger.

Security and data protection

  • Nothing leaves your machines. GitHub Pages serves this page as one static file; after that it loads no scripts, fonts or trackers from anywhere and sends nothing, and your browser enforces that: the page's Content-Security-Policy (the first lines of its source) allows no source anywhere (default-src 'none'), so it cannot connect to anything, and lets only its own inline scripts run, each named by its SHA-256. page.test.mjs checks that policy against the page on every CI run. The command-line script makes no network calls, reads only the input you name, and writes no files. make-zip.mjs checks the shipped script for network, eval, child-process, environment and file-write patterns on every CI run and refuses to build if one appears. The one declared pattern is URL text, because the gate reads the links in a draft; it never visits them.
  • No processor, no transfer, no account. Your drafts and receipts are processed on your own machine, under your control. Nobody receives them, so there is no third-party processing and no international transfer to assess under UK GDPR or GDPR.
  • No supply chain to trust. Zero dependencies: no npm packages, no third-party libraries or services, no model weights, no binaries. It uses only Node.js's own built-in modules, and the package is text files only.
  • Deterministic and re-checkable. The same draft and receipt give the same verdict, byte for byte: CI compares the script's output with committed reports on every push. Anyone can re-run the mutation test on the same bytes; the receipts name the exact kernel, tests and witness by SHA-256.
  • Tamper-evident records. Sealed post-receipts and the hash-chained ledger use SHA-256, tested against known vectors. Change any field of a sealed post-receipt and it no longer verifies; change any ledger entry and verification names the first entry that changed.

Risks, answered straight

  • It does not fetch. Whoever builds the receipt must probe for real (the 200, the CI result, the test run). A false receipt gets a false pass: the gate proves the post matches the receipt, not that the receipt is true. Build the receipt from your CI's own probes, never by hand.
  • It checks the checkable only. "Fastest on the market", "SOC 2 certified", "GDPR compliant" and "independently audited" are not links, scores, percents, multipliers, live, CI or verified claims; no build probe can prove them, so the gate does not read them. Keep your legal and compliance review for those. That is a stated limit, not a hidden one.
  • It catches rounding-up, not a determined evader. A score, percent or multiplier of any length is read ("1000%", "12345/12345", "70 percent", "3x", "10×"), but numbers written as words ("fifty out of fifty", "a hundred percent", "twice as fast", "tenfold") and a multiplier with a spaced letter x ("3 x faster") are not. It guards against an agent or a busy person overclaiming by habit; pair it with a human read for anything adversarial.
  • Numbers are matched as written, as whole numbers. A percent, a K/N score or a multiplier is backed only when a receipt fact states the same number: "3%" is not backed by a fact saying "30%", nor "1/4" by "11/40", nor "3x" by "13x" or "3.5x", and a percent needs a fact written as a percent ("30%", "30 percent"). It does not convert units or round; write facts as measured.
  • Some ordinary text reads as a score. A date with its year ("5/11/2026") is left alone, but a date without one ("11/05") and "24/7" look exactly like K/N scores, so they are refused until a fact states them. Write dates with the year or the month's name, and back "24/7" with a fact (your support rota).
  • Tamper-evident, not signed, by design. The seals and the ledger hash-verify, so any change is detectable; they do not prove who sealed them. Proving that needs a key, and this tool is built to need none (no account, no key, nothing to hold). If you must prove who published, sign the sealed post-receipt with the release-signing key you already use.
  • Not independently audited. It is mutation-tested in public CI on every push, and every mutant the tests do not catch carries a written argument that it cannot change any output.
  • The cost case is a model, not a measurement. It takes your figures; the saving is reviewer time given back, not an invoice cancelled.

    COO

    • What happens when a true post is refused? The refusal names the claim and why. Usually the evidence exists but is not in the receipt: add it as a fact (a measured figure, or a link fact for an outbound link) and run again. There is no override switch in the gate; publishing anyway is a person's decision, made outside it, and the refusal stays on record (in CI's log, and on the ledger if you keep one). Two you will meet: "24/7" and a date with no year ("11/05") read as K/N scores; back "24/7" with a fact, and write the date with its year ("5/11/2026").
    • Does it work in other languages? Links, K/N scores, percentages written with "%" and multipliers are checked in any language. The status words ("live", "launched", "CI green", "verified") and "percent" are matched in English only, so in another language those claims go unchecked.
    • How exactly do we add a fact? A fact is a pair in the receipt's facts list: a key, and the measured statement as you would quote it, for example {"key": "review-time", "value": "cut review time 30% on one team"}. A percent, a K/N score or a multiplier in the draft is backed when a fact's value states the same number as a whole number, so "review time down 30%" passes against that fact, and "down 70%" and "down 3%" do not. Write a percent in a fact as a percent ("30%" or "30 percent"), a score as K/N ("41/43", "4.9/5"), and a multiplier as written ("ran 3x faster on job A"). An outbound link is whitelisted with a fact keyed link whose value is the exact URL.
    • Does it fit our build system? Any build system works: the receipt is five fields (url, live, ci, witness, facts) you fill from whatever your pipeline already measures. A malformed receipt is refused with the reason, never guessed at.
    • Can we change the rules? Not by configuration, on purpose: fixed rules are what make every team's answer the same. What you control is the receipt (facts and whitelisted links). To change a rule you change kernel.mjs (MIT); its tests and the mutation gate then show exactly what the change broke.
    • What changes for the team? Reviewers stop cross-checking links, statuses and scores; writers get named words to fix; release engineers add one CI step. Nobody needs training beyond reading one refusal.

    White paper: proof before publication

    The problem

    People and AI agents who write about their own work round up. "Live" goes out before anything answered; "all tests pass" goes out when CI failed; a perfect score goes out when the tests caught most, not all. These are the claims a reader takes as fact, because they look checkable, and one wrong one discredits every true claim beside it. As AI agents write more release notes, changelogs and launch posts, the volume outruns any human check.

    The method

    Split a draft into two parts: the claims a receipt could prove (links, live status, CI status, verified/clean, K/N scores, percentages, multipliers) and everything else. Take a build-receipt produced by real probes: did the URL return 200, what did CI conclude, what did the mutation test score, which facts were measured. Back each checkable claim only by the field that can prove it, and refuse the post if one is not backed, naming the words. Seal a passed post to its receipt with two hashes, and log every decision on a hash chain.

    Why no AI judge

    A model grading marketing copy has its own error rate and gives no guarantee of the same answer twice; it is the false confidence this gate exists to refuse. A rule gives the same answer every time, can be read in full, and can be tested to destruction. The gate's whole job is to be boring and certain about a narrow thing.

    The evidence

    The kernel has 54 tests. The witness mutation test (v0.6) made 98 single-operator changes to it and the tests caught 96; the other 2 were reviewed as unable to change any output and are recorded with a written reason each; 0 survived. The cost-case kernel: 14 tests, 28 of 28 changes caught. The shipped script reproduces the committed example reports byte for byte. All of it re-runs on GitHub's runner at every push, in public.

    What it does not prove

    That the receipt is true (whoever builds it must probe for real); that the prose is fair, clear or persuasive; that a writer determined to evade it cannot (numbers in words pass). It proves one thing: the post did not claim more than its receipt shows.

    Where it fits

    After whatever writes the post (a person, an AI agent, a post generator) and before whatever publishes it. In our own publishing pipeline the prose is scrubbed first, this gate then checks the scrubbed text (so a scrub that changed a claim would be refused), and only then does the posting rail apply its own rate limits: no receipt, no post. That pipeline keeps its own vendored copy of the kernel, so it has the fixes the buyer walks found only once that copy is re-vendored from here; the copy on this page and in the agent script is always this repository's current, gated one.
